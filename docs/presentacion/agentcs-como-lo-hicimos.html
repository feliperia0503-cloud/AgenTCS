Metodología, agentes y patrones de AgenTCS

Todo lo que hay aquí está tomado del código real del repositorio. Úsenlo para ensayar: si el jurado pregunta, cada afirmación se puede mostrar en el código o en pantalla.

💡 La idea en una frase: la IA propone (reglas y código); la plataforma ejecuta, mide y decide (compilación, comparación y controles).
01

Metodología de trabajo

Cómo construimos la solución como equipo de tres, y cómo la solución trabaja una migración.

1Primero los contratos

Lo primero que escribimos fue copilot/contracts/: especificación neutral, tipos, casos y reporte de equivalencia. Luego se congeló.

"Con el contrato fijo, tres máquinas trabajaron en paralelo sin pisarse."

2Guiada por especificación

No traducimos línea a línea. Extraemos una especificación de negocio —reglas, tipos, contrato de entrada y salida— y generamos el código nuevo desde ella.

"El puente entre el lenguaje viejo y el nuevo es la especificación, no la sintaxis."

3Humano en el ciclo

El flujo se detiene en la fase 4. Nada se genera hasta que una persona aprueba, ajusta o rechaza cada regla. Las de baja confianza (< 0,7) exigen comentario.

"La IA no decide sola qué es una regla de negocio."

4Verificación diferencial

Legacy y código nuevo se ejecutan con las mismas entradas y se comparan campo por campo, con tolerancia cero.

"La equivalencia se demuestra, no se promete."

5Decisiones documentadas

Cada decisión de arquitectura quedó en un ADR: 7 en docs/adr/ (caso, portabilidad, agnosticismo, interfaz, motor, ingesta, oráculo nivel A).

6Pruebas sin gastar créditos

Más de 120 pruebas automáticas usan un modelo simulado. El modelo real solo se usa en corridas de verdad, y sus respuestas quedan en caché.

03

El motor de autocorrección

El corazón técnico (ADR-005). Repite generar → compilar → comparar → retroalimentar hasta lograr la equivalencia o una condición de parada.

Parámetros reales (loop.py)

Máximo de intentos5
Meseta: intentos sin mejora antes de parar2
Presupuesto de tokens por corrida600.000
Similitud0,7 × casos que pasan + 0,3 × campos iguales
Qué se entregaEl mejor intento, no el último
RegresiónCaso que pasaba y vuelve a fallar → se marca
Reintentos si el JSON no cumple el esquema2

"A cada intento le decimos exactamente qué caso falló, en qué campo, qué esperábamos, qué obtuvimos y qué regla está implicada."

04

Técnicas

🎯 Oráculo de tres niveles

  • A: el legacy se ejecuta de verdad (GnuCOBOL, Mono, JDK…).
  • B: pares entrada/salida que aporta el usuario.
  • C: referencia generada desde la especificación aprobada.

"El nivel se declara siempre; C nunca se presenta como si fuera A."

🧮 Decimales exactos

Todo dinero y tasa pasa por un tipo neutral con escala y modo de redondeo explícitos (HALF_UP, HALF_EVEN, DOWN…). Los casos rechazan números con punto flotante: los decimales viajan como texto.

🧠 Memoria de lecciones, no ajuste fino

El modelo no se reentrena. Las lecciones de corridas anteriores se guardan y se inyectan en el prompt del generador.

✅ Salida estructurada validada

Cada respuesta del modelo se valida con Pydantic. Las reglas que citan líneas que no existen se descartan; las variables que no aparecen en el código bajan la confianza.

💾 Caché y modo replay

Cada respuesta se guarda por hash SHA-256 del modelo y el prompt. Con AGENTCS_LLM_REPLAY=1 la demo corre sin internet y sin gastar créditos.

🛡️ Sanitización previa

Antes de cada llamada al modelo se enmascaran secretos, correos y números de tarjeta (validados con el algoritmo de Luhn).

📦 Ejecución en sandbox

El código generado corre sin la API key en su entorno, con tiempo límite y rutas protegidas.

🔎 Escaneo del resultado

gitleaks y Semgrep con reglas propias revisan el código generado: secretos, punto flotante en dinero y eval. Sin herramienta, se declara "escaneo incompleto".

05

Patrones de diseño

Puertos y adaptadores

Arquitectura hexagonal en la propia solución: el núcleo no conoce ningún lenguaje; cada origen y destino es un "pack" que implementa una interfaz.

"Es el patrón que hace posible el agnosticismo."

Registro de plugins + Strategy

El pack se elige en tiempo de ejecución según el lenguaje. Agregar un lenguaje de origen ejecutable es un YAML y un Markdown.

Pipeline con controles de calidad

8 fases; cada una tiene una condición de salida (gate) que se muestra en pantalla.

Golden master / pruebas diferenciales

La salida del legacy es la verdad; el código nuevo tiene que reproducirla exactamente.

Arquitectura limpia en lo generado

Dominio sin frameworks; el código del framework (Spring, ASP.NET, NestJS…) queda aislado en infrastructure/.

Seguridad por defecto

Anti-SSRF al clonar repositorios, protección contra zip slip, límites de tamaño y errores con acción sugerida que nunca exponen trazas.

06

Preguntas probables del jurado

Intenten responder en voz alta antes de abrir cada una.

¿Cómo saben que el código nuevo hace lo mismo que el viejo?
Ejecutamos ambos con las mismas entradas y comparamos cada campo con tolerancia cero. La pantalla dice qué nivel de evidencia tiene el resultado: A si el legacy se ejecutó de verdad, B si usamos pares del usuario, C si es una referencia generada.
¿Y si la IA extrae mal una regla?
Dos barreras. Primero, una persona revisa cada regla con sus líneas de origen antes de generar nada. Segundo, con oráculo nivel A el esperado sale del legacy real, así que un error de extracción aparece como diferencia. Con nivel C ese error podría repetirse en ambos lados; por eso lo declaramos como la evidencia más débil.
¿Funciona solo con COBOL?
No. El núcleo no conoce ningún lenguaje. Hoy hay packs de origen para COBOL, PL/SQL, Delphi, PHP, RPG, VB6, .NET y Java legacy, y destinos Java, C#, TypeScript y Python. Un lenguaje desconocido usa un segmentador genérico con confianza reducida, y eso se declara.
¿Es un sistema multiagente?
Son siete agentes especializados orquestados por un motor determinista. No conversan entre sí: cada uno hace una tarea acotada y la plataforma valida lo que producen antes de usarlo.
¿El modelo aprende o se reentrena?
No se reentrena. Usamos memoria de lecciones: al final de una corrida se resumen los errores y esas lecciones se inyectan en el prompt de corridas futuras.
¿Qué pasa con los datos sensibles del cliente?
Antes de cualquier llamada al modelo se sanitizan secretos, correos y tarjetas. En la demo solo usamos datos sintéticos. El .env nunca se versiona y el código generado se escanea con gitleaks y Semgrep.
¿Cómo manejan los redondeos?
Todo valor monetario pasa por un tipo neutral con escala y modo de redondeo explícitos. Nunca punto flotante. Los casos de prueba incluyen bordes de redondeo a propósito, y el motor corrige si el destino redondea distinto.
¿Qué pasa si no logra el 100 %?
Se detiene por meseta, por máximo de intentos o por presupuesto, entrega el mejor intento y la fase de verificación queda en rojo con las diferencias visibles. Nunca se oculta un fallo.
¿Qué pasa si se cae internet en la demo?
Modo replay: las respuestas del modelo están en caché por hash del prompt, así que la corrida se reproduce sin internet. El análisis, la compilación y la comparación siguen ejecutándose de verdad.
¿Qué tan difícil es instalarlo?
Un comando: docker compose up --build y abrir http://localhost:8000. Todos los compiladores y runtimes viven dentro de la imagen.
